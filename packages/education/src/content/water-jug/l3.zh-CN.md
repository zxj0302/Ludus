## 1. 玩 · Play

你有 N 个水壶，容量分别为 c₁, c₂, ..., cₙ（正整数），和一个无限水源。每一步可以执行以下三种操作之一：

- **Fill(i)**：将第 i 个壶装满到容量上限
- **Empty(i)**：将第 i 个壶倒空
- **Pour(i, j)**：从壶 i 倒水到壶 j，直到壶 i 为空或壶 j 满

目标：让**某一个壶**中的水量恰好等于目标值 T。

> 经典案例：在电影《虎胆龙威3》中，布鲁斯·威利斯需要用 3 加仑和 5 加仑的壶量出 4 加仑水来拆除炸弹。

试一试：3L 和 5L 壶 → 4L 水，你能找到最短步数吗？

---

## 2. 思考挑战 · Think

> 给定容量 a、b，哪些 T 可达？哪些不可达？如何一眼判断一个目标是否可能？

思考路径：
1. 试一些例子：a=6, b=10。能量出 1L 吗？2L 呢？3L 呢？4L 呢？
2. 注意每次操作改变的水量总是某个值的倍数。这个值是什么？
3. 能否不经过 BFS，直接用数学公式判断可解性？
4. 当壶数 N 从 2 变为 3 或更多时，状态空间如何增长？会影响 BFS 的效率吗？

## 3. 揭示 · Reveal

### §3.1 形式化定义

**倒水问题 (Water Jug Problem)**：

- **输入**：N 个正整数 c₁, ..., cₙ（容量），一个正整数 T（目标水量），满足 T ≤ max(c₁, ..., cₙ)
- **状态**：(w₁, ..., wₙ)，0 ≤ wᵢ ≤ cᵢ
- **初始状态**：(0, 0, ..., 0) — 所有壶为空
- **操作**：
  - Fill(i)：wᵢ ← cᵢ，前提 wᵢ < cᵢ
  - Empty(i)：wᵢ ← 0，前提 wᵢ > 0
  - Pour(i, j)：amount = min(wᵢ, cⱼ − wⱼ)；wᵢ ← wᵢ − amount；wⱼ ← wⱼ + amount，前提 amount > 0
- **目标**：∃i 使得 wᵢ = T
- **优化目标**：最少操作数

### §3.2 复杂度归类

| 问题变体 | 复杂度 | 说明 |
|---------|--------|------|
| 判定可达性 | **P** | 裴蜀定理：T % gcd(c₁, ..., cₙ) == 0。O(N log max(c)) |
| 最短步数（固定 N） | **P** | BFS，状态空间 = Π(cᵢ+1)，多项式时间 O(V+E) |
| 最短步数（N 可变） | **P** | 仍为多项式——状态空间与 N 无关，仅与容量有关 |
| 最少操作数（一般有向图 BFS） | **P** | 标准的无权图最短路径问题 |

**为什么是 P 而非 NP？** 状态空间大小 = Π(cᵢ+1)，其中 cᵢ 以**数值**（而非位数）计入输入规模。对 2 壶问题，若 c₁, c₂ ≤ 12，状态空间 ≤ 169，BFS 毫秒级完成。即便是 3 壶最大容量 12 的情形，状态空间 ≤ 2197，仍微不足道。这是典型的多项式时间可解问题。

### §3.3 数学基础：裴蜀定理与 GCD

#### 定理 (Bézout's Identity)

> 对任意非零整数 a、b，存在整数 x、y 使得 **ax + by = gcd(a, b)**。并且 gcd(a, b) 是 a 和 b 的整数线性组合能表示的最小正整数。

**必要性证明概要**：任意操作（装满、倒空、倒水）改变的水量都是各壶容量的整数线性组合。因此任意可达状态的每个 wᵢ 都可表示为 Σ kⱼ·cⱼ（kⱼ 为整数），从而是 gcd(c₁, ..., cₙ) 的倍数。若 T 不可被 GCD 整除，则永不可达。

**充分性证明概要**：由扩展欧几里得算法，存在整数 x, y 使得 ax + by = g = gcd(a, b)。通过适当地装满/倒空操作序列，可以实现以 g 为步长的任意增量，从而达成任意 g 的倍数。

#### 例子

| 容量 (a, b) | GCD | 可达目标 |
|-------------|-----|---------|
| (3, 5) | 1 | `{1, 2, 3, 4, 5}` — 全部可达 |
| (4, 6) | 2 | `{2, 4, 6}` — 只有偶数可达 |
| (6, 10) | 2 | `{2, 4, 6, 8, 10}` — 只有偶数可达 |
| (5, 7) | 1 | `{1, 2, 3, 4, 5, 6, 7}` — 全部可达 |
| (8, 12) | 4 | `{4, 8, 12}` — 只有 4 的倍数可达 |
| (8, 12, 20) | 4 | `{4, 8, 12, 16, 20}` — 3 壶情形 |

#### 推论：生成可解谜题的充分条件

取任意两个互质的容量 (a, b) 且 gcd(a, b) = 1，则对所有 T ≤ max(a, b)，谜题 (a, b, T) 均是可解的。这是关卡生成器最常用的模式。

### §3.4 状态空间分析

2 壶问题，状态空间 = (c₁+1)(c₂+1)。每个状态有 2 个装满 + 2 个倒空 + 2 个倒水 = 至多 6 条出边。

| 最大容量 | 2 壶状态空间 | 3 壶状态空间 |
|---------|------------|------------|
| 5 | 36 | 216 |
| 8 | 81 | 729 |
| 12 | 169 | 2197 |

### §3.5 步骤上界分析

BFS 按层扩展，保证找到的是最短路径。但最短路径**最长**能有多长？知道这个上界有两个意义：(1) 确定 BFS 在最坏情况下需要搜索多深；(2) 它为 §5.4 的难度公式提供了分母。

#### 平凡图论上界

由于 BFS 每个状态最多访问一次，最短路径长度不可能超过状态空间大小减一：

```
maxDepth ≤ stateSpace − 1
```

对 (3,5)：stateSpace=36，上界 35；对 (11,12)：stateSpace=156，上界 155。但这个上界**非常松**——实际最优深度远小于状态空间大小。

#### 容量和上界（2 壶问题）

对两壶问题，存在一个紧得多的上界：

> **定理**：容量为 a、b 的两壶问题，BFS 最短路径长度 ≤ a + b − gcd(a, b)。

**直觉论证**：每次 Fill 操作将总水量恰好增加一个壶的容量，每次 Empty 操作将总水量恰好减少一个壶的容量。总水量始终在 0 到 a+b 之间。Pour 不改变总水量。最短路径中，Fill 和 Empty 的总次数必然与目标水量所需的"净水量变化"相关——而扩展欧几里得算法构造出的解路径，恰好将目标水量表达为容量的整数线性组合，步数 ≤ a + b − gcd(a, b)。BFS 保证找到的路径不会比构造解更长。

**形式化**（gcd = 1 情形）：由裴蜀定理，存在整数 x、y 使得 ax + by = 1。若 x > 0，反复装满壶 a 并倒入壶 b（b 满时倒空）；若 y > 0，则对称操作。每次"装满→倒出"至多 2 步，总操作数 ≤ |x| + |y| ≤ a + b − 1（扩展欧几里得算法最小系数对的性质）

**gcd > 1 情形**：等效于求解容量 a/g、b/g、目标 T/g 的缩放问题，上界变为 (a + b) / g − 1。

#### 紧致性示例

上界在"相邻容量 + 目标为 1"时最接近紧致：

| 容量 (a, b) | gcd | 目标 | 容量和上界 | 实际 BFS 深度 | 紧致率 |
|-------------|-----|------|-----------|-------------|--------|
| (3, 5) | 1 | 1 | 8 | 6 | 75% |
| (5, 7) | 1 | 1 | 12 | 8 | 67% |
| (7, 11) | 1 | 1 | 18 | ~16 | ~89% |
| (11, 12) | 1 | 1 | 23 | ~21 | ~91% |
| (4, 6) | 2 | 2 | 4 | 3 | 75% |
| (8, 12) | 4 | 4 | 4 | 4 | 100% |

相邻容量（如 11 和 12）必然互质，扩展欧几里得算法需要最多步数达到系数 1，因此实际深度最接近理论上界。相比之下，(3,5)→1 的实际深度只有 6，远低于上界 8——说明小容量时上界仍偏保守，但已远紧于状态空间上界 35。

#### 代码中的上界

当前难度系统使用的上界：

```
maxDepth = max(sum(capacities), 6)
```

`max(..., 6)` 保底让极小谜题（如 (2,3)→1）也能获得有意义的分数。该公式既有数学原则支撑，又在经验上涵盖所有实际出现的 BFS 深度。

#### N 壶推广

对 N 个壶，保守上界：

```
maxDepth ≤ sum(capacities) / minGCD
```

其中 `minGCD = gcd(c₁, ..., cₙ)`。总水量每次至多改变一个容量，可达状态的颗粒度是 minGCD。对容量 ≤ 12 的 3 壶问题，sum ≤ 36，最坏上界 36。但实践中即使 3 壶谜题的最优深度也很少超过 25——这就是旧代码将 maxDepth 固定为 25 的经验依据。当前公式 `max(sum(capacities), 6)` 既严谨又在经验上充分。

## 4. 求解 · Solve

### §4.1 BFS 算法伪代码

```
Algorithm BFS-WaterJug(capacities c[1..n], target T):
  Input:  capacities array, target amount
  Output: shortest operation sequence (or "unsolvable")

  root ← (0, 0, ..., 0)         // 所有壶为空
  visited ← {root}               // 状态去重集合
  queue ← [root]                 // BFS 队列
  parent[root] ← null            // 路径回溯

  while queue is not empty:
    state ← queue.dequeue()
    if ∃ i such that state.jugs[i] == T:
      return reconstructPath(state, parent)  // 找到目标

    OPS ← legalOperations(state)  // 装满/倒空/倒水
    for each op in OPS:
      next ← applyOp(state, op)
      if next not in visited:
        visited.add(next)
        parent[next] ← (state, op)
        queue.enqueue(next)

  return "unsolvable"
```

### §4.2 正确性分析

- **完备性 (Completeness)**：BFS 系统地探索所有可达状态。由于状态空间有限（≤ Π(cᵢ+1)），若解存在，BFS 必将在有限步内找到它。
- **最优性 (Optimality)**：BFS 按深度层扩展。所有深度为 d 的状态在深度 d+1 之前被探索，因此第一个找到的解路径最短。这是无权图 BFS 的核心性质——每条边代价相同（均为 1 步）。
- **复杂度**：时间 O(V + E)，空间 O(V)，其中 V 是可达状态数，E 是总出边数。对 2 壶 c₁, c₂ ≤ 12：V ≤ 169, E ≤ 169 × 6 ≈ 1014，毫秒级完成。

### §4.3 求解器方法对比

| 方法 | 时间复杂度 | 空间复杂度 | 最优解 | 可判定性 | 适用场景 |
|------|-----------|-----------|--------|---------|---------|
| **BFS** | O(Π(cᵢ+1)) | O(Π(cᵢ+1)) | ✅ 保证 | ✅ 完备 | 小容量（cᵢ ≤ 12）— 本实现 |
| DFS | O(Π(cᵢ+1)) | O(最大深度) | ❌ 不保证 | ✅ 完备 | 仅判定可达性 |
| 裴蜀定理 | O(N log max(c)) | O(1) | ❌ 不适用 | ✅ 判定 | 快速可解性检查 |
| 扩展欧几里得 | O(log min(a,b)) | O(1) | ❌ 不适用 | ✅ 判定+构造系数 | 2 壶 GCD=1 的直接构造 |
| A* | O(V log V) | O(V) | ✅ 保证 | ✅ 完备 | 大状态空间需启发式引导 |
| IDA* | O(bʳᵉᶠ) | O(d) | ✅ 保证 | ✅ 完备 | 内存受限的大深度搜索 |

对本游戏（cᵢ ≤ 12），BFS 是最佳选择：实现简单、最优保证、速度足够。

## 5. 出题 · Create

### §5.1 可解性保证（必要性与充分性）

**必要性**：裴蜀定理给出必要条件——T 必须是 gcd(c₁, ..., cₙ) 的倍数。生成器在随机选择容量后，先计算 GCD，再在可达成目标集合中随机选取 T。

**充分性**：若 T % gcd == 0，**一定存在**一系列操作可达。这由裴蜀定理+状态空间 bfs 的完备性共同保证。

```typescript
// 生成器核心逻辑
function pickTarget(capacities: number[]): number {
  let g = capacities[0];
  for (let i = 1; i < capacities.length; i++)
    g = gcd(g, capacities[i]);

  // 收集所有可达目标（g 的倍数，不超过最大容量）
  const maxCap = Math.max(...capacities);
  const achievable = [];
  for (let t = g; t <= maxCap; t += g)
    achievable.push(t);

  return achievable[randomIndex(achievable.length)];
}
```

### §5.2 唯一性讨论

BFS 总是返回**某个**最短路径，但不保证**唯一**。多个等长最优路径可能存在。例如：

- 3L+5L→4L：最短步数 = 6。存在多条不同的 6 步路径（例如可以先装满 3L vs 先装满 5L）。
- 当 gcd(a,b) = 1 且容量较小时，通常存在多条对称的最优解。

生成器记录 BFS 返回的最短路径长度用于难度评分，但不声称该路径唯一。

### §5.3 已知最优解

BFS 按层扩展的数学性质保证了最优性——第一个找到的解就是最短路径。这不需要额外验证。

生成器生成谜题后：
1. 调用 `solveWaterJug(state)` 运行 BFS
2. 若 `solvable = true`，记录 `solutionLength`（最短步数）
3. 将 `solutionLength` 存入 `level.optimalSteps`
4. 传递给 `computeWaterJugDifficulty()` 用于难度评分

### §5.4 难度因素与公式

#### 困难度公式

```
depthScore   = round((min(optimalDepth, maxDepth) / maxDepth) × 80)
spaceBonus   = round(min(stateSpace / 2197, 1) × 20)
score        = min(depthScore + spaceBonus, 100)
```

其中：
- `optimalDepth` 是 BFS 求得的最短步数
- `maxDepth = max(sum(capacities), 6)` —— §3.5 推导的数学上界
- `stateSpace = Π(cᵢ+1)` —— 状态空间大小
- `2197 = 13³` —— 3 壶 × 容量 12 的最大状态空间

公式分为两个组件：
1. **深度分（0–80）**：最优步数占理论最大步数的比例，占主导地位
2. **状态空间加分（0–20）**：状态空间越大，即使步数相同，寻找路径的认知负担也更重

`max(..., 6)` 保底确保极小容量谜题仍能获得有意义的难度分数。

#### 难度因素贡献表

| 因素 | 权重 | 说明 |
|------|------|------|
| 最优路径深度 | ⭐⭐⭐⭐⭐ | 最直接的因素：深度大→步数多→更困难 |
| 容量大小 | ⭐⭐⭐⭐ | 容量越大，状态空间越大，搜索空间越大 |
| 壶的数量 | ⭐⭐⭐ | 3 壶的状态空间 ≈ 容量的三次方，显著增加搜索复杂性 |
| GCD 关系 | ⭐⭐ | GCD = 1 时更易构造解（更多路径可选）；GCD > 1 时约束更紧 |
| 目标值大小 | ⭐ | 目标靠近最大容量时，通常需要更多步骤 |
| 状态空间 | ⭐ | 直接贡献 0–20 分加成，与容量和壶数高度相关 |

#### 难度档位分布

| 档位 | 分数范围 | 容量范围 | 壶数 | 典型最优步数 | 典型状态空间 |
|------|---------|---------|------|-------------|------------|
| 简单 | 1–33 | 2–5 | 2 | ≤5 | ≤36 |
| 中等 | 34–66 | 5–8 | 2–3 | 5–12 | ≤729 |
| 困难 | 67–100 | 8–12 | 2–3 | 10–23 | ≤2197 |

### §5.5 关卡生成器伪代码

```
Algorithm GenerateWaterJugLevel(difficultyRange):
  Input:  [scoreMin, scoreMax]
  Output: Level { initialState, difficulty, optimalSteps, ... }

  // 1. 确定容量范围
  if scoreMax ≤ 33:
    capMin, capMax ← 2, 5;  numJugs ← 2
  else if scoreMax ≤ 66:
    capMin, capMax ← 5, 8;  numJugs ← random(2, 3)
  else:
    capMin, capMax ← 8, 12; numJugs ← random(2, 3)

  bestResult ← null; bestDistance ← ∞

  // 2. 拒绝采样：最多尝试 100 次
  for attempt in 1..100:
    capacities ← [random(capMin, capMax) for _ in 1..numJugs]
    // 确保不是所有壶容量相同
    if numJugs ≥ 2 and capacities[0] == capacities[1]:
      capacities[1] ← random(capMin, capMax)

    // 3. 从非平凡目标中选取（优先较难的目标）
    candidates ← pickTargetsByDifficulty(capacities)
    target ← candidates[random(0, ceil(|candidates|/2) - 1)]  // 只取前半段

    if not isSolvable(capacities, target): continue

    // 4. BFS 求解
    state ← createInitialState(capacities, target)
    solution ← solveWaterJug(state)
    if not solution.solvable: continue
    optimalSteps ← solution.stats.solutionLength
    if optimalSteps < 3: continue  // 拒绝平凡谜题（≤2 步）

    // 5. 计算难度分数
    difficulty ← computeWaterJugDifficulty(state, optimalSteps)
    score ← difficulty.score

    // 6. 若分数落在目标范围，直接返回
    if scoreMin ≤ score ≤ scoreMax:
      return { ..., initialState: state, difficulty, optimalSteps, ... }

    // 7. 否则跟踪最佳候选（最接近目标范围的）
    distance ← score < scoreMin ? scoreMin - score : score - scoreMax
    if distance < bestDistance:
      bestDistance ← distance; bestResult ← (state, optimalSteps, difficulty)

  // 8. Fallback: 返回最佳候选（即使分数不完全匹配）
  if bestResult exists: return bestResult as Level

  // 9. Ultimate fallback: 经典谜题 (3,5) → 4
  return classicLevel(3, 5, 4)
```

### §5.6 验证清单

每个生成的关卡在返回前需通过以下验证：

- [x] `isSolvable(capacities, target)` → true（裴蜀定理）
- [x] `target > 0` 且 `target ≤ max(capacities)`
- [x] 至少 2 壶，容量 ≥ 2
- [x] BFS `solution.solvable` → true（经验验证）
- [x] `optimalSteps > 0` — 目标是可达的且非初始状态
