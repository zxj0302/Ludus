# Sudoku — Complete Mathematics & Algorithms

## 1. Play

Same as L2.

## 2. Think

Beyond the L2 questions, consider:

- **Minimum givens**: 17 is the known minimum for a standard 9×9 Sudoku with a unique solution — verified by McGrath (2012) through massive computer search, but a formal mathematical proof remains an open problem.
- **Logical deduction vs. guessing**: Human solvers rely on a library of patterns (naked singles, hidden singles, pairs, X-Wing, Swordfish, etc.); computers use backtracking + constraint propagation and brute-force through it. **Difficulty = depth of the human reasoning chain** — a computer doesn't care; it only looks at the search tree size.
- **Worst-case complexity**: Naive backtracking for 9×9 has a branching factor of ~9, yielding $9^{81}$ in the worst case — constraint propagation reduces the effective branching factor to ~3.5.

## 3. Reveal

### 3.1 Exact Cover Formulation

Knuth (2000) formalized the Sudoku-to-Exact-Cover transformation in his landmark "Algorithm X + Dancing Links" paper.

**Matrix dimensions**: $R$ rows × $C$ columns
- $R = 9 \times 9 \times 9 = 729$ (each cell × 9 candidate digits)
- $C = 81 + 81 + 81 + 81 = 324$ (four constraint types)

Let row $(i, j, k)$ mean "place digit $k$ in cell $(i, j)$". This row has a 1 in the following 4 constraint columns:

1. **Cell constraint** $c_{cell}(i, j)$: cell $(i, j)$ must contain exactly one digit
2. **Row constraint** $c_{row}(i, k)$: row $i$ must contain digit $k$ exactly once
3. **Column constraint** $c_{col}(j, k)$: column $j$ must contain digit $k$ exactly once
4. **Box constraint** $c_{box}(b, k)$: box $b$ must contain digit $k$ exactly once

where box index $b = 3 \times \lfloor i/3 \rfloor + \lfloor j/3 \rfloor$.

**Mathematical definition**: Let $M \in \{0, 1\}^{729 \times 324}$ where $M_{(i,j,k), t} = 1$ iff candidate $(i,j,k)$ involves constraint $t$. Solving Sudoku is equivalent to:

> Find a set of row indices $S \subseteq \{1, \dots, 729\}$ such that for every column $c$,
> $$\sum_{r \in S} M_{r,c} = 1 \quad (\text{every column is covered by exactly one row})$$

### 3.2 Complexity Classification

- **Complexity Class**: **NP-complete** (for generalized $n \times n$)
- **Justification**: Reduce the $n \times n$ Latin square completion problem (known NP-complete) to $n \times n$ Sudoku completion. Latin squares only constrain rows and columns; Sudoku adds $\sqrt{n} \times \sqrt{n}$ box constraints, making it at least as hard.
- **9×9 special case**: Although the general problem is NP-complete, the fixed 9×9 instance has a constant-size search space. In practice, DLX solves any 9×9 Sudoku in microseconds.

## 4. Solve

### 4.1 Algorithm X Framework

Algorithm X is the general backtracking algorithm for solving Exact Cover problems:

```
function Algorithm_X(Matrix M):
    if M has no columns: return SUCCESS       // all constraints covered
    Choose a column c (column selection heuristic)
    cover(c)
    for each row r in column c:
        record r as part of the solution
        for each column j in row r (j ≠ c):
            cover(j)
        Algorithm_X(remaining submatrix of M)
        if SUCCESS: return SUCCESS
        for each column j in row r (j ≠ c):
            uncover(j)
    uncover(c)
    return FAILURE
```

### 4.2 Column Selection Heuristic

The most critical heuristic in DLX is the **S heuristic (minimum column)** — always pick the column with the fewest nodes. This minimizes the branching factor:

$$c^* = \arg\min_{c} |\text{col\_candidates}(c)|$$

Intuition: process the tightest constraints first, pruning the search tree as early as possible.

### 4.3 Dancing Links Data Structure: Core Operations

Dancing Links represents the matrix as a toroidal doubly linked list. Each non-zero element is a node:

```
class DLXNode {
    left, right: DLXNode    // neighbors in the row
    up, down: DLXNode       // neighbors in the column
    column: ColumnNode      // pointer to column header
}

class ColumnNode extends DLXNode {
    size: number            // nodes in this column (for heuristic)
    name: string            // column identifier (debugging)
}
```

#### cover(c) Operation

```pseudo
function cover(c: ColumnNode):
    // Remove column c from the row header
    c.right.left = c.left
    c.left.right = c.right
    // For each row r in column c (traversing down)
    for each row r in column c:
        // For each node n in row r (traversing right, n ≠ r)
        for each node n in row r:
            // Remove node n from its column
            n.down.up = n.up
            n.up.down = n.down
            n.column.size -= 1
```

#### uncover(c) Operation

```pseudo
function uncover(c: ColumnNode):
    // Reverse traversal (opposite order from cover, ensuring correct restoration)
    for each row r in column c (going up, reverse order):
        for each node n in row r (going left, reverse order, n ≠ r):
            n.column.size += 1
            n.down.up = n
            n.up.down = n
    // Reattach column c to the row header
    c.right.left = c
    c.left.right = c
```

**Key property**: The time complexity of cover/uncover is linear in the number of nodes removed/restored — not the full matrix size. Since each candidate assignment touches at most 4 constraint columns (cell, row, column, box), each row node has at most 4 neighbors. Therefore DLX's overall complexity is proportional to the **number of candidates**, not $729 \times 324$.

### 4.4 End-to-End Solving Pipeline

```
function solveSudoku(grid: 9×9):
    // 1. Build the 729×324 exact cover matrix
    M = buildExactCoverMatrix()
    
    // 2. For each given cell, add its row to the solution and cover its columns
    for each given cell (i, j) with value v:
        row = encodeRow(i, j, v)
        for each column c ∈ row:
            cover(c)
    
    // 3. Run Algorithm X on the remaining submatrix
    return Algorithm_X(M)
```

## 5. Create

> Unlike §3's formal definition, §5 addresses the core question: **how do we guarantee that a generated Sudoku puzzle is well-formed?**
> A well-formed puzzle must satisfy several guarantees, each mathematically or algorithmically verifiable.

---

### 5.1 Guarantee I: Solvability (At Least One Solution Exists)

#### Problem

Given a partially filled grid, does a legal complete filling exist?

#### Criterion

For 9×9 Sudoku, simply run the DLX solver and check whether it returns at least one solution. This is guaranteed by Algorithm X's completeness: it searches the full solution space, so if a solution exists, it will be found.

#### How Generation Guarantees It

- **Digging method**: Start from a complete valid grid and remove cells one by one. Since the complete grid is already one solution, the resulting puzzle is trivially solvable as long as uniqueness is maintained after each removal.
- **Random fill method**: Use DLX to solve an empty grid (producing a random valid complete grid), then dig → guaranteed solvable.
- **Verification method**: If the puzzle was generated by another means, verify solvability with DLX. If no solution → discard and retry.

> **Conclusion**: The digging method guarantees solvability at the source. This is the default strategy for Sudoku generators.

---

### 5.2 Guarantee II: Unique Solution

#### Problem

Does the puzzle admit **more than one** legal complete filling?

#### Criterion

$$ \text{Puzzle has a unique solution} \iff |\text{solutions}(\text{puzzle})| = 1 $$

For 9×9 Sudoku, enumerating all solutions is feasible (the constraints are tight enough that the solution space is typically small).

#### How Generation Guarantees It — The Digging Algorithm

1. Generate a **complete valid grid** (all 81 cells filled) using DLX
2. Order the cells for potential removal (using a removal strategy)
3. For each candidate cell:
   a. Temporarily remove the digit
   b. Run `countSolutions(puzzle, limit=2)` — stop as soon as the 2nd solution is found
   c. If exactly 1 solution → removal confirmed valid; if >1 solution → restore the digit
4. Move to the next candidate, repeating until no more cells can be removed

```
function generateUniquePuzzle():
    // 1. Generate a complete grid
    full = generateCompleteGrid()        // use DLX for random solving
    puzzle = copy(full)
    
    // 2. Determine removal order (random shuffle or difficulty-based)
    cells = shuffle(all81Cells())
    
    for each (i, j) in cells:
        saved = puzzle[i][j]
        puzzle[i][j] = 0                 // remove digit
        
        // 3. Check uniqueness
        solutions = countSolutions(puzzle, limit=2)
        if solutions != 1:
            puzzle[i][j] = saved         // restore, cannot remove
    
    return puzzle
```

#### Optimization

`countSolutions(puzzle, limit=2)` stops immediately upon finding the second solution — it never enumerates all solutions. For most cells, the check completes in microseconds to milliseconds.

**Known results for 9×9 standard Sudoku**:
- **Minimum givens**: 17 (extensively verified via computer search)
- **Minimum givens with symmetry**: 18 (verified to exist)
- **Pattern concentration**: most 17-given puzzles cluster in specific structural patterns

---

### 5.3 Guarantee III: Known Optimal Solution

#### Problem

For Sudoku, "optimal solution" doesn't mean "fewest moves" (there are no moves in Sudoku). It means **unique solution**. A puzzle with multiple solutions is considered invalid in standard Sudoku.

#### Criterion

$$ \text{Puzzle is valid} \iff \text{countSolutions}(\text{puzzle}) = 1 $$

#### How Generation Guarantees It

During the digging process, `countSolutions` is the core verification function. If `countSolutions(puzzle, limit=2) == 1`, the puzzle is valid.

---

### 5.4 Guarantee IV: Difficulty Control

#### Problem

How do we quantify a Sudoku puzzle's difficulty and precisely control it during generation?

#### Difficulty Factor Framework

| Factor | Symbol | Quantification | Effect on Difficulty | Controllability |
|--------|--------|---------------|---------------------|-----------------|
| Number of givens | $g$ | count of givens | Fewer givens → more empty cells → larger search tree → harder. $g=17$ is extreme; $g=30+$ is usually easy | **Continuously tunable** |
| Reasoning chain depth | $d$ | Average depth of consecutive deductions in backtracking | Greater depth → more reasoning steps needed → harder | **Indirectly controllable** (via digging strategy) |
| Digging order strategy | — | Strategy for choosing which cell to remove next | Remove "easy-to-deduce" cells first → stable but easy; remove "critical cells" first → hard | **Strategy-tunable** |
| Search tree size | $\|T\|$ | Number of nodes expanded during DLX backtracking | Larger search tree → more human reasoning required → harder | **Measurable** (post-generation) |
| Required technique level | — | Human solving techniques needed (naked single → hidden single → pair → X-Wing → ...) | Higher technique → sharper pattern recognition needed → harder | **Indirectly controllable** |

#### Digging Strategies and Their Difficulty Impact

| Strategy | Description | Given Distribution | Difficulty Tier |
|----------|------------|-------------------|-----------------|
| **Random digging** | Remove cells in completely random order | Uniform distribution | 🟡 Easy-Medium |
| **Corner-first digging** | Remove cells systematically from one corner | Diagonal decreasing density | 🟡 Easy |
| **Symmetric digging** | Remove cells in pairs symmetric about center | Center-symmetric distribution | 🟠 Medium (aesthetically pleasing) |
| **Critical-cell digging** | At each step, among cells where countSolutions=1, remove the one maximizing search tree | Concentrated in constraint-dense regions | 🔴 Hard |
| **Target $g$ digging** | Remove until exactly $g$ givens remain | Depends on strategy | Tunable (by $g$) |

#### Difficulty Tier Mapping

| Tier | Given Count | Human Experience | Typical Solve Time |
|------|------------|------------------|-------------------|
| 🟢 Beginner | 36–45+ | Obvious singles throughout, most cells uniquely determined | 1–3 min |
| 🟡 Easy | 30–35 | Basic elimination needed, no long reasoning chains | 3–8 min |
| 🟠 Medium | 25–29 | Pairs technique needed, moderate reasoning chains | 8–15 min |
| 🔴 Hard | 22–24 | X-Wing or higher techniques required | 15–30 min |
| ⚫ Expert | 17–21 | Multiple advanced techniques chained, long reasoning chains | 30+ min |

### 5.5 Generator Implementation Framework

```
class SudokuGenerator {
    // 1. Generate a complete solution
    generateCompleteGrid(): Grid {
        // Start from empty grid, use DLX to find the first solution
        return DLX_solve(emptyGrid())[0]
    }
    
    // 2. Dig to generate the puzzle
    generatePuzzle(targetGivens: number): Puzzle {
        const full = this.generateCompleteGrid()
        const cells = this.shuffleCellsWithStrategy(targetGivens)
        
        for (const (i, j) of cells) {
            const saved = full[i][j]
            full[i][j] = 0
            if (countSolutions(full, 2) !== 1) {
                full[i][j] = saved
            }
            if (countGivens(full) <= targetGivens) break
        }
        
        return { puzzle: full, solution: originalFull }
    }
    
    // 3. Difficulty verification
    estimateDifficulty(puzzle: Grid): Difficulty {
        const givens = countGivens(puzzle)
        const searchTreeSize = DLX_searchTreeSize(puzzle)
        return difficultyFromFactors(givens, searchTreeSize)
    }
}
```

#### Difficulty Verification Loop

Every generated puzzle must pass the following checks before publication:

1. **Solvability**: DLX returns at least one solution (guaranteed by digging).
2. **Uniqueness**: `countSolutions(puzzle, 2) == 1`.
3. **Given count matches target**: givens within the target range.
4. **Difficulty score consistent**: generated difficulty tier matches human spot checks.
5. **Human playability spot-check**: randomly sample 5% of generated puzzles for manual playtesting.

### 5.6 Digging vs. Alternatives

| Property | Digging | Random Fill + Verify | Template |
|----------|---------|---------------------|----------|
| Solvability guarantee | ✅ 100% (constructive) | ⚠️ Requires verification | ✅ Template guarantee |
| Unique solution guarantee | ✅ Incremental verification | ⚠️ Requires countSolutions | ⚠️ Requires verification |
| Difficulty control | ✅ Precise given count control | ❌ No precise control | ⚠️ Fixed by template |
| Implementation complexity | Medium | Low | High (many templates needed) |
| Puzzle diversity | ✅ Extremely high | ✅ High | ❌ Limited by template library |
| **Conclusion** | **Default strategy** | Prototyping only | Suitable for consistent style |
