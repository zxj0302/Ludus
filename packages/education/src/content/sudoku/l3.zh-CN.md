## 2. 思考 · Think

除了 L2 中的问题，再思考：

- **已知数密度**：17 个已知数是 9×9 标准数独的唯一解最少已知数下限——这是 McGrath (2012) 通过大规模计算机搜索验证的结论，但尚未被数学证明（仍然是开放问题）。
- **逻辑推理 vs. 猜测**：人类解题依赖"模式库"（唯一余数、摒除法、数对、X-Wing、Swordfish 等）；计算机只用回溯 + 约束传播即可碾压。**难度 = 人类需要推理步数的深度**——计算机不在乎，它只看搜索树的大小。
- **最坏情况的时间复杂度**：对于 9×9 数独回溯搜索的最坏情况分支因子约为 9，需要 $9^{81}$ 的朴素穷举——约束传播将有效分支因子降低到 ~3.5 左右。

## 3. 揭示 · Reveal

### 3.1 精确覆盖形式化

数独到精确覆盖问题的转化由 Knuth (2000) 在其"Algorithm X + Dancing Links"论文中系统化。

**矩阵规模**：$R$ 行 × $C$ 列
- $R = 9 \times 9 \times 9 = 729$（每个格子 × 9 个候选数字）
- $C = 81 + 81 + 81 + 81 = 324$（四种约束）

记行 $(i, j, k)$ 表示"在格子 $(i, j)$ 填数字 $k$"，该行在以下 4 个约束列上标 1：

1. **格子列** $c_{cell}(i, j)$：格子 $(i, j)$ 必须恰好填一个数字
2. **行列** $c_{row}(i, k)$：第 $i$ 行必须恰好有一个数字 $k$
3. **列列** $c_{col}(j, k)$：第 $j$ 列必须恰好有一个数字 $k$
4. **宫列** $c_{box}(b, k)$：第 $b$ 个宫格必须恰好有一个数字 $k$

其中宫格索引 $b = 3 \times \lfloor i/3 \rfloor + \lfloor j/3 \rfloor$。

**数学定义**：设矩阵 $M \in \{0, 1\}^{729 \times 324}$，其中 $M_{(i,j,k), t} = 1$ 当且仅当候选 $(i,j,k)$ 涉及约束 $t$。求解数独等价于：

> 找到一组行索引 $S \subseteq \{1, \dots, 729\}$，使得对每一列 $c$，
> $$\sum_{r \in S} M_{r,c} = 1 \quad (\text{每列恰好被一行覆盖})$$

### 3.2 复杂度归类

- **复杂度类**：**NP-complete**（一般化 $n \times n$）
- **论证**：将 $n \times n$ 拉丁方完成问题（已知 NP-complete）归约到 $n \times n$ 数独完成问题。拉丁方的约束仅为"每行每列不重"；数独增加了 $n$ 个 $\sqrt{n} \times \sqrt{n}$ 宫格约束，因此最少同样难。
- **9×9 特例**：虽然一般化问题 NP-complete，9×9 的固定规模搜索空间是常数。实践中 DLX 在微秒级解任意 9×9 数独。

## 4. 求解 · Solve

### 4.1 Algorithm X 框架

Algorithm X 是求解精确覆盖问题的通用回溯算法：

```
function Algorithm_X(Matrix M):
    if M 没有列: return SUCCESS        // 所有约束已被覆盖
    选一列 c（列选择启发式）
    cover(c)
    for each 行 r ∈ 列 c 中的行:
        记录 r 为解的一部分
        for each 列 j ∈ 行 r (j ≠ c):
            cover(j)
        Algorithm_X(M 的剩余部分)
        if SUCCESS: return SUCCESS
        for each 列 j ∈ 行 r (j ≠ c):
            uncover(j)
    uncover(c)
    return FAILURE
```

### 4.2 列选择启发式

DLX 中最关键的启发式是 **S heuristic（最小列启发式）**：每次选择当前节点数最少的列进行覆盖。这样可以最大程度减少分支因子：

$$c^* = \arg\min_{c} |\text{col\_candidates}(c)|$$

直观理解：约束最紧的列（候选最少）先处理，尽早剪枝。

### 4.3 Dancing Links（舞蹈链）数据结构的核心

Dancing Links 的核心创新是用循环双向链表表示精确覆盖矩阵。矩阵的非零元素用节点对象表示，每个节点包含：

```
class DLXNode {
    left, right: DLXNode    // 左右邻节点
    up, down: DLXNode       // 上下邻节点
    column: ColumnNode      // 所在列头
}

class ColumnNode extends DLXNode {
    size: number            // 该列中的节点数（对于启发式）
    name: string            // 列标识符（调试用）
}
```

#### cover(c) 操作

```pseudo
function cover(c: ColumnNode):
    // 从行头中移除列 c
    c.right.left = c.left
    c.left.right = c.right
    // 遍历 c 列的每一行
    for each row r in column c (going down):
        // 遍历行 r 的所有节点
        for each node n in row r (going right, n ≠ r):
            // 从列中移除节点 n
            n.down.up = n.up
            n.up.down = n.down
            n.column.size -= 1
```

#### uncover(c) 操作

```pseudo
function uncover(c: ColumnNode):
    // 反向遍历（与 cover 顺序相反，保证状态正确恢复）
    for each row r in column c (going up, reverse order):
        for each node n in row r (going left, reverse order, n ≠ r):
            n.column.size += 1
            n.down.up = n
            n.up.down = n
    // 将列 c 重新挂回行头
    c.right.left = c
    c.left.right = c
```

**关键性质**：cover/uncover 的时间复杂度与删除/恢复的节点数成线性关系，而非矩阵大小。由于每个候选赋值最多出现在 4 个约束列中（格子、行、列、宫），每个行节点最多有 4 个邻居，因此 DLX 的整体复杂度与**候选数**成正比，而非 $729 \times 324$。

### 4.4 整体求解流程

```
function solveSudoku(grid: 9×9):
    // 1. 构建 729×324 精确覆盖矩阵
    M = buildExactCoverMatrix()
    
    // 2. 将已知数对应的行加入解集并覆盖其列
    for each given cell (i, j) with value v:
        row = encodeRow(i, j, v)
        for each column c ∈ row:
            cover(c)
    
    // 3. 在剩余子矩阵上运行 Algorithm X
    return Algorithm_X(M)
```

## 5. 出题 · Create

> 与 §3"形式化定义"不同，§5 的核心问题是：**如何保证生成的数独关卡合理**？
> 一个"合理"的关卡须满足以下保证，每个都可被数学或算法严格验证。

---

### 5.1 保证一：可解性（至少存在一个解）

#### 问题

给定一个初始部分填充的棋盘，是否存在一个合法的完整填充？

#### 判定

对于 9×9 数独，只需运行 DLX 求解器检查是否至少返回一个解。这由 DLX 算法本身的完备性保证：Algorithm X 搜索全部解空间，若存在解则必定找到。

#### 生成保证

- **挖空法（Digging）**：从合法完整棋盘开始，逐步移除数字。因为完整棋盘天然是一个解，每一步移除只要不破坏唯一解性，新棋盘自然可解。
- **随机填充法**：先用 DLX 求解一个随机完整棋盘，再挖空 → 天然保证可解。
- **验证法**：若通过其他方式生成了初始棋盘，用 DLX 验证至少存在一个解。若无解 → 丢弃重试。

> **结论**：挖空法从源头保证可解性。这是数独生成器的默认策略。

---

### 5.2 保证二：唯一解

#### 问题

给定棋盘，是否存在**不止一种**合法的完整填充？

#### 判定

$$ \text{棋盘有唯一解} \iff |\text{solutions}(\text{board})| = 1 $$

对 9×9 数独，枚举全部解是可行的（虽然极端最坏情况下解的数量可能很大，但约束足够紧，通常解空间很小）。

#### 生成保证

**挖空法核心流程**：
1. 用 DLX 生成一个**合法完整棋盘**（所有 81 格已填）
2. 按一定顺序枚举待移除的格子
3. 对每个候选移除：
   a. 暂时移除该格数字
   b. 运行 `countSolutions(board, limit=2)` —— 只需检查到第 2 个解即停止
   c. 若解数恰为 1 → 确认移除有效，保留；若解数 > 1 → 该格不可移除，恢复数字
4. 继续处理下一个候选格子，直到不能再移除为止

```
function generateUniquePuzzle():
    // 1. 生成完整棋盘
    full = generateCompleteGrid()        // 使用 DLX 随机求解
    puzzle = copy(full)
    
    // 2. 确定挖空顺序（随机打乱或按难度排序）
    cells = shuffle(all81Cells())
    
    for each (i, j) in cells:
        saved = puzzle[i][j]
        puzzle[i][j] = 0                 // 移除数字
        
        // 3. 检查唯一解
        solutions = countSolutions(puzzle, limit=2)
        if solutions != 1:
            puzzle[i][j] = saved         // 恢复，不能移除此格
    
    return puzzle
```

#### 剪枝优化

`countSolutions(board, limit=2)` 一旦找到 2 个解就立即停止搜索，不需要枚举所有解。对于大部分格子，移除后的求解耗时在微秒到毫秒级。

**9×9 标准数独的已知结果**：
- **最少已知数**：17（已有大量实例验证）
- **对称模式的最少已知数**：18（已验证存在）
- **最少的普遍性**：几乎所有 17 个已知数的数独都集中在某些模式上

---

### 5.3 保证三：已知最优解（≈ 唯一解）

#### 问题

对于数独，"最优解"通常不是指"最少步数"（因为数独不存在"操作步数"概念），而是指**唯一解**。如果一个关卡有多个解，它被认为是不合法的（在标准数独中）。

#### 判定

$$ \text{关卡合法} \iff \text{countSolutions}(\text{puzzle}) = 1 $$

#### 生成保证

在挖空过程中，`countSolutions` 是核心验证函数。若 `countSolutions(puzzle, limit=2) == 1`，则关卡合法。

---

### 5.4 保证四：难度可控

#### 问题

如何量化一个数独关卡的难度，并在生成时精确控制？

#### 难度因素体系

| 因素 | 符号 | 量化方法 | 对难度的影响 | 可控性 |
|------|------|---------|-------------|--------|
| 已知数数量 | $g$ | $\text{givens}$ 的个数 | $g$ 越少→空格越多→搜索树越大→越难。$g=17$ 是最难的极端；$g=30$+ 通常很简单 | **连续可调** |
| 推理链深度 | $d$ | 回溯搜索中连续推理的平均深度 | 深度越大→需要跨越的推理步骤越多→越难 | **间接可控**（通过挖空策略） |
| 挖空顺序策略 | — | 按不同策略选择挖空顺序 | 先挖"容易推理"的格→生成过程稳定但难度偏低；优先挖"关键格"→难度偏高 | **策略可调** |
| 搜索树大小 | $\|T\|$ | DLX 回溯中扩展的节点数 | 搜索树越大→人类解题的推理量越大→越难 | **可度量**（生成后可计算） |
| 所需技巧等级 | — | 人类解题需要的推理技巧（唯一余数→摒除法→数对→X-Wing→…） | 越高级的技巧→需要越敏锐的模式识别→越难 | **间接可控** |

#### 挖空策略对难度的影响

| 策略 | 描述 | 已知数分布 | 难度档位 |
|------|------|-----------|---------|
| **随机挖空** | 完全随机顺序移除数字 | 均匀分布 | 🟡 简单-中等 |
| **从一角推进** | 从棋盘一角开始系统化移除 | 对角线式递减 | 🟡 简单 |
| **优先挖对称格** | 每步挖一组关于中心对称的格子 | 中心对称分布 | 🟠 中等（视觉愉悦） |
| **优先挖"关键格"** | 每次移除后 countSolutions=1 的情况下，选使搜索树最大的格移除 | 集中于约束密集区 | 🔴 困难 |
| **目标 $g$ 控制** | 设定目标已知数 $g$（如 22），挖空直到只剩 $g$ 个已知数 | 取决于挖空策略 | 可控（由 $g$ 决定） |

#### 难度分类

| 档位 | 已知数范围 | 人类体验 | 典型耗时 |
|------|-----------|---------|---------|
| 🟢 入门 | 36–45+ | 一眼可看穿，多数格可唯一确定 | 1–3 分钟 |
| 🟡 简单 | 30–35 | 需要基本摒除法，无长推理链 | 3–8 分钟 |
| 🟠 中等 | 25–29 | 需要数对技巧，有中等推理链 | 8–15 分钟 |
| 🔴 困难 | 22–24 | 需要 X-Wing 或更高级技巧 | 15–30 分钟 |
| ⚫ 专家 | 17–21 | 需要多种高级技巧串联，推理链长 | 30 分钟以上 |

### 5.5 生成器实现框架

```
class SudokuGenerator {
    // 1. 生成完整解
    generateCompleteGrid(): Grid {
        // 从空网格开始，用 DLX 找到第一个解即为完整棋盘
        return DLX_solve(emptyGrid())[0]
    }
    
    // 2. 挖空生成谜题
    generatePuzzle(targetGivens: number): Puzzle {
        const full = this.generateCompleteGrid()
        const cells = this.shuffleCellsWithStrategy(targetGivens)
        
        for (const (i, j) of cells) {
            const saved = full[i][j]
            full[i][j] = 0
            if (countSolutions(full, 2) !== 1) {
                full[i][j] = saved
            }
            if (countGivens(full) <= targetGivens) break
        }
        
        return { puzzle: full, solution: originalFull }
    }
    
    // 3. 难度验证
    estimateDifficulty(puzzle: Grid): Difficulty {
        const givens = countGivens(puzzle)
        const searchTreeSize = DLX_searchTreeSize(puzzle)
        // 结合已知数和搜索树大小给出难度分
        return difficultyFromFactors(givens, searchTreeSize)
    }
}
```

#### 难度验证闭环

生成的每个关卡在发布前，须经过以下验证：

1. **可解性**：DLX 至少返回一个解（挖空法天然保证）。
2. **唯一性**：`countSolutions(puzzle, 2) == 1`。
3. **已知数数量符合目标**：$\text{givens}$ 在目标范围内。
4. **难度分与预期一致**：生成的难度分类与人类速测结果一致。
5. **人类可玩性抽查**：随机抽取 5% 关卡进行人工试玩。

### 5.6 挖空法优势

| 特性 | 挖空法 | 随机填充+验证 | 模板法 |
|------|--------|-------------|--------|
| 可解性保证 | ✅ 100%（构造保证） | ⚠️ 需验证 | ✅ 模板保证 |
| 唯一解保证 | ✅ 逐步验证 | ⚠️ 需 countSolutions | ⚠️ 需验证 |
| 难度控制 | ✅ 可精确控制已知数数量 | ❌ 不可精确控制 | ⚠️ 模板固定 |
| 实现复杂度 | 中等 | 低 | 高（需要大量预设模板） |
| 关卡多样性 | ✅ 极高 | ✅ 高 | ❌ 受限于模板库 |
| **结论** | **默认策略** | 仅适用于原型 | 适合有固定风格时 |
