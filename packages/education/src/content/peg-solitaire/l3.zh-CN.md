## 1. 玩 · Play

专业向看孔明棋，第一件事不是把它“数学化到不好玩”，而是解释为什么它好玩：它是一台很小的不可逆机器。每步都少一枚棋子，所以你不能靠来回移动撤销错误；你的每个局部选择都会永久改变未来的状态图。

**Hook 1：孔明棋像一场“没有后悔药的垃圾回收”。** 你想把棋子回收到 1 枚，但每回收一枚，也可能删掉一条未来的边。好解法不是“尽快变少”，而是“让剩下的棋子仍然能互相服务”。

本实现锁定英式 33 孔盘，并使用三档目标：

- `le3`：剩余 \(\le 3\)。
- `one-any`：剩余恰好 1 枚，位置不限。
- `one-center`：剩余恰好 1 枚且在中心孔 16。

**Rigorous claim 1：从 \(n\) 枚棋子到 \(k\) 枚棋子，任何合法路线步数都是 \(n-k\)。** 这是由单步净减少 1 枚的守恒式直接推出。经典中心空盘有 32 枚棋子，因此任何一枚终局均为 31 步；“31 步”不是求解器优化出来的，而是目标棋子数决定的。

## 2. 思考挑战 · Think

孔明棋的难点来自两个层面：局部合法性很简单，全球可达性很复杂。你可以一眼判断某一步是否合法，却很难一眼判断 20 步后会不会把自己锁死。

**Hook 2：反直觉局面：越空越可能更难。** 搜索树的分支因子并不随棋子数单调上升。中盘可能有很多跳法；残局如果棋子互相隔开，分支数会突然归零。难度不是“棋子越多越难”这么粗糙。

可验证地分析一个局面时，可以分三层：

1. **计数层**：剩余棋子数决定最少还要走多少步。
2. **连通/桥层**：合法跳法需要相邻的两枚棋子和一个空孔。
3. **目标层**：`one-center` 不只要消到 1 枚，还要控制最终落点。

**Rigorous claim 2：合法移动图是有向无环图。** 若把每个状态当作节点、合法跳法当作边，那么每条边都会让 `popcount` 减 1，因此不可能形成环。实现里仍然使用 visited 集合，不是为了防环，而是为了合并不同路线到达的同一状态与 D4 等价状态。

**Hook 3：D4 对称像“把八张自拍认成同一个人”。** 一个局面旋转 90 度、180 度、270 度，或做水平/垂直/对角翻转后，搜索意义相同。人类也会这样偷懒：先解决左翼，再用镜像理解右翼。

## 3. 揭示抽象 · Reveal

### 3.1 bitmask 状态

本仓库把 33 个孔映射到一个 JavaScript `number`。因为 \(2^{33}-1\) 远小于 `Number.MAX_SAFE_INTEGER`，单个安全整数足以精确表示所有孔位；不需要 BigInt，也不需要双 32 位分片。

令 \(B\) 为 bitmask，孔 \(i\) 有棋子当且仅当：

\[
\left\lfloor \frac{B}{2^i} \right\rfloor \bmod 2 = 1
\]

一次走法 \((a,b,c)\) 的语义是：

\[
B' = (B \setminus \{a,b\}) \cup \{c\}
\]

在代码里就是清掉 `from` / `over` 两位，再设置 `to` 一位。

**Rigorous claim 3：全配置上界为 \(2^{33}\)，但搜索并不需要枚举全部配置。** 经典开局只会访问从该初态可达的状态；目标越宽松（如 `le3`），搜索越早停止。这个上界是复杂度警钟，不是实际运行路径。

### 3.2 D4 对称规范化

英式十字盘在正方形 7×7 网格内对称，保留 8 个二面体变换：

\[
D_4 = \{e, r_{90}, r_{180}, r_{270}, h, v, d, a\}
\]

实现中预先构造 8 个 permutation。对一个 bitmask，求出 8 个变换后的 bitmask，取数值最小者作为 `canonicalKey`。

**Rigorous claim 4：`canonicalKey` 在 D4 轨道内不变。** 若 \(x\) 与 \(y\) 只相差一个 D4 变换，则它们的 8 个变换集合相同，因此最小代表相同。这样 visited 集合按轨道去重，而不是按原始摆放去重。

**Hook 4：对称剪枝不是魔法加速器，是“少看重复剧集”。** 它不改变是否有解，也不发明新走法；它只是发现你正在看同一集的横屏版、竖屏版和镜像版。

### 3.3 搜索方法

本实现选择预算内的混合策略：

- 小残局或显式 `findShortest`：BFS，保证单位步长下首次到达目标为最短。
- 深局面：DFS + visited + D4 canonical key，在时间预算内优先找可行解。
- trace 复用 `search-tree`，记录 `nodesExplored`、`solutionLength`、`maxDepth`、`terminated`、`symmetry`、`search`。

伪代码：

```ts
visited = { canonicalKey(start.pegs) }
frontier = [start]
while frontier not empty and within timeBudget:
  state = pop(frontier) // BFS uses queue, DFS uses stack
  for move in legalMoves(state):
    next = applyMove(state, move)
    key = canonicalKey(next.pegs)
    if key in visited: continue
    if meetsGoal(next.pegs, goal): return path + move
    visited.add(key)
    frontier.push(next)
return timeout or exhausted
```

**Rigorous claim 5：DFS 找到一条解不等于证明最短。** BFS 的最短性依赖“按深度层展开”；DFS 会深入某一分支，可能先撞见较长解。本 UI 和文档只在 BFS/已知残局元数据支持时谈最短，不把一般 DFS 结果包装成最优定理。

### 3.4 复杂度诚实

一般化孔明棋属于指数级状态空间搜索问题；英式 33 孔盘是固定小实例，能被工程优化和经典知识处理，但这不意味着任意盘面族有多项式求解器。这里要区分：

- **固定实例**：33 孔英式盘，状态空间有限。
- **输入族**：盘面大小可增长时，状态数随孔数指数增长。
- **本实现承诺**：给出可运行求解器、预算、trace 和 timeout 信号。
- **本实现不承诺**：证明任意生成局面的唯一最短解。

## 4. 求解器演示 · Solver

可视化层读取 `trace.type === 'search-tree'` 且仅接入 `peg-solitaire` entry。它展示探索节点数、解长、耗时、最大深度、终止原因，以及解路径上的跳跃列表。这个视图不是完整搜索树渲染器，而是搜索证据面板：让玩家知道求解器做了多少工作、用了什么模式、是否真的到达目标。

**Hook 5：搜索可视化要防止“看起来很科学”。** 一个漂亮的图如果不显示 timeout、DFS 非最短、uniqueSolution=false，就会误导玩家。我们宁愿把边界讲清，也不靠炫图制造确定性幻觉。

Worker 路径也要诚实：插件 metadata 标记 `webWorker: true`，Web 的 solver worker 直接导入 `@ludus/games/src/peg-solitaire/solver`，避免把 React 渲染层带进 worker chunk。桌面/移动壳复用同一 Web 代码；若 Worker 不可用，store 层仍有纯 TS fallback。

**Rigorous claim 6：Worker 改变线程位置，不改变算法语义。** 同一个 `solvePegSolitaire` 在主线程测试与 Worker 路径中使用；Worker 的价值是避免深搜阻塞 UI，而不是提供不同答案。

与 Lights Out 的对比尤其重要：

- Lights Out 是 GF(2) 线性系统，按按钮可交换，求解近似“解方程”。
- Peg Solitaire 是不可逆状态搜索，顺序重要，不能把走法简单相加抵消。
- Lights Out 可讨论秩、零空间、解空间；Peg Solitaire 更自然讨论可达性、分支、对称轨道和搜索预算。

## 5. 出题 · Create

生成器的 v1 目标是“可玩且诚实”，不是“发表级唯一性证明”。它根据 `difficultyRange` 映射目标：

\[
[1,33]\to le3,\quad [34,66]\to one\text{-}any,\quad [67,100]\to one\text{-}center
\]

然后从 curated puzzles 中筛选目标匹配的残局，必要时做轻量挖空，再调用求解器验证可达。返回 level 时：

- `optimalSteps` 来自求解器路径长度或已知元数据。
- `uniqueSolution` 固定为 false。
- `generatedBy = generatePegSolitaireLevel`。
- 难度由棋子数、合法跳法数、目标严格度、中心占用等因素估计。

**Rigorous claim 7：当前难度分是启发式，不是定理。** `getDifficulty` 把 peg load、mobility pressure、goal strictness 和 center penalty 组合成 0-100 分。它解释“为什么看起来难”，但不证明人类体感或最短搜索深度完全匹配。

**Hook 6：出题器的底线像餐厅的卫生证，不像米其林星级。** 它先保证“能吃”：可达目标；再逐步追求“好吃”：节奏、唯一性、惊喜、可教学。v1 先把卫生证挂出来，不假装已经摘星。

后续可以扩展三类更强保证：

- 唯一解：枚举或计数全部可达解，成本显著上升。
- 唯一最短：搜索到最短层并计数该层解。
- 难度校准：用更多特征（死局密度、对称破坏、中心回归距离）训练或拟合体感评分。

开放问题留给玩家和开发者：一个“好”的孔明棋关卡，是最短解难找，还是最后几步最有戏剧性？
