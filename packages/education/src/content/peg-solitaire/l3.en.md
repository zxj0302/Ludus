## 1. 玩 · Play

The professional way to read Peg Solitaire is not to drain the fun out of it, but to explain why the fun works: it is a small irreversible machine. Every move removes one peg, so you cannot shuffle pieces back and forth to undo a bad local choice. Each move permanently changes the future state graph.

**Hook 1: Peg Solitaire is “garbage collection without undo.”** You want to collect the board down to one peg, but every collected peg may also delete a future bridge. A good solution is not “remove material quickly”; it is “leave material that can still cooperate.”

This implementation fixes the English 33-hole board and exposes three targets:

- `le3`: leave \(\le 3\) pegs.
- `one-any`: leave exactly 1 peg anywhere.
- `one-center`: leave exactly 1 peg at center hole 16.

**Rigorous claim 1: from \(n\) pegs to \(k\) pegs, every legal route has exactly \(n-k\) moves.** This follows directly from the one-peg net decrease per move. The classic center-empty start has 32 pegs, so any one-peg finish uses 31 moves. The number 31 is forced by counting, not discovered by clever search.

## 2. 思考挑战 · Think

Peg Solitaire has simple local legality and hard global reachability. You can check one move at a glance, but you cannot usually see whether the board will still have a route twenty moves later.

**Hook 2: the counterintuitive part is that emptier can be harder.** The branching factor is not monotone in the peg count. Midgames may have many jumps; endgames can suddenly have zero if pegs become isolated. Difficulty is not just “more pegs means harder.”

A useful analysis has three layers:

1. **Counting layer**: remaining peg count fixes how many moves are still required.
2. **Bridge layer**: a legal jump requires two adjacent pegs plus an empty landing hole.
3. **Target layer**: `one-center` is not only about reducing to one peg; it is about controlling the final landing site.

**Rigorous claim 2: the legal-move graph is directed acyclic.** Treat each state as a node and each legal jump as an edge. Every edge reduces `popcount` by 1, so no directed cycle can exist. The implementation still uses a visited set, not to prevent cycles, but to merge different routes and D4-equivalent positions that reach the same abstract state.

**Hook 3: D4 symmetry is “recognizing eight selfies as the same person.”** Rotate a board by 90, 180, or 270 degrees, or reflect it horizontally, vertically, or diagonally: for search, those positions can be the same problem. Human solvers do this too when they solve one wing and reason about the mirrored wing.

## 3. 揭示抽象 · Reveal

### 3.1 Bitmask State

The repository represents the 33 holes with one JavaScript `number`. Since \(2^{33}-1\) is far below `Number.MAX_SAFE_INTEGER`, all hole masks are exact safe integers. BigInt and split 32-bit masks are unnecessary for this board.

Let \(B\) be the bitmask. Hole \(i\) contains a peg exactly when:

\[
\left\lfloor \frac{B}{2^i} \right\rfloor \bmod 2 = 1
\]

A move \((a,b,c)\) means:

\[
B' = (B \setminus \{a,b\}) \cup \{c\}
\]

In code, this clears the `from` and `over` bits and sets the `to` bit.

**Rigorous claim 3: the full configuration upper bound is \(2^{33}\), but the solver does not enumerate all configurations.** From a fixed start, it only visits reachable states until it reaches the selected target or exhausts its budget. The upper bound is a complexity warning, not a description of the actual execution path.

### 3.2 D4 Canonicalization

The English cross board sits inside a symmetric 7x7 grid, so it preserves the eight dihedral transforms:

\[
D_4 = \{e, r_{90}, r_{180}, r_{270}, h, v, d, a\}
\]

The implementation precomputes eight permutations. For a bitmask, it transforms the mask by each permutation and chooses the smallest numeric mask as `canonicalKey`.

**Rigorous claim 4: `canonicalKey` is invariant within a D4 orbit.** If \(x\) and \(y\) differ only by a D4 transform, their eight transformed masks form the same set, so their minimum representative is identical. The visited set therefore deduplicates by symmetry orbit rather than raw screen orientation.

**Hook 4: symmetry pruning is not magic acceleration; it is skipping reruns.** It does not change solvability and does not invent moves. It notices that you are watching the same episode in landscape, portrait, and mirror mode.

### 3.3 Search Method

This implementation uses a budgeted hybrid:

- Small endgames or explicit `findShortest`: BFS, where first target discovery is shortest under unit move costs.
- Deep positions: DFS + visited + D4 canonical key, prioritizing a feasible route within the time budget.
- Trace type: `search-tree`, with `nodesExplored`, `solutionLength`, `maxDepth`, `terminated`, `symmetry`, and `search`.

Pseudocode:

```ts
visited = { canonicalKey(start.pegs) }
frontier = [start]
while frontier not empty and within timeBudget:
  state = pop(frontier) // BFS uses queue, DFS uses stack
  for move in legalMoves(state):
    next = applyMove(state, move)
    key = canonicalKey(next.pegs)
    if key in visited: continue
    if meetsGoal(next.pegs, goal): return path + move
    visited.add(key)
    frontier.push(next)
return timeout or exhausted
```

**Rigorous claim 5: a DFS solution is not automatically a shortest-proof certificate.** BFS shortestness depends on expanding by depth layers. DFS may find a deeper route first. The UI and docs only talk about shortestness when BFS or known puzzle metadata supports it; they do not turn general DFS output into an optimality theorem.

### 3.4 Complexity Honesty

Generalized Peg Solitaire is a state-space search problem with exponential growth. The English 33-hole board is a fixed small instance that engineering and classic knowledge can handle, but that does not imply a polynomial algorithm for arbitrary growing board families.

Separate these claims:

- **Fixed instance**: the English 33-hole board has a finite, bounded state space.
- **Input family**: when the board grows, occupied/empty configurations grow exponentially.
- **This implementation promises**: a runnable solver, budgeted search, trace data, and timeout reporting.
- **This implementation does not promise**: a proof of unique shortest solution for every generated board.

## 4. 求解器演示 · Solver

The visualization layer reads `trace.type === 'search-tree'` only through the `peg-solitaire` entry. It shows explored nodes, solution length, elapsed time, max depth, termination reason, and a list of jumps on the returned route. It is not a full universal search-tree renderer; it is an evidence panel that explains what the solver actually did.

**Hook 5: search visualization must resist looking “scientific” without being honest.** A beautiful graph that hides timeout, DFS non-shortestness, or `uniqueSolution=false` misleads the player. This view prefers clear limits over false certainty.

The Worker story is also intentionally plain. The plugin metadata advertises `webWorker: true`, and the web solver worker imports `@ludus/games/src/peg-solitaire/solver` directly so the React render layer does not leak into the worker chunk. Desktop and mobile shells reuse the same web code; if the Worker path is unavailable, the store can still use the pure TypeScript fallback.

**Rigorous claim 6: Worker execution changes the thread, not the algorithm.** The same `solvePegSolitaire` powers main-thread tests and the Worker route. The Worker prevents deep search from blocking the UI; it is not a second solver with different semantics.

The contrast with Lights Out is the teaching payoff:

- Lights Out is a GF(2) linear system; button presses commute, and solving is close to “solve equations.”
- Peg Solitaire is irreversible state search; order matters, and moves cannot be freely added and canceled.
- Lights Out naturally teaches rank, nullspace, and solution spaces. Peg Solitaire naturally teaches reachability, branching, symmetry orbits, and search budgets.

## 5. 出题 · Create

The v1 generator aims to be playable and honest, not a research-grade uniqueness prover. It maps `difficultyRange` to a target:

\[
[1,33]\to le3,\quad [34,66]\to one\text{-}any,\quad [67,100]\to one\text{-}center
\]

It then samples curated puzzles for that target, optionally applies light dig-out variation, and runs the solver to verify reachability. The returned level records:

- `optimalSteps` from the solver route or known puzzle metadata.
- `uniqueSolution: false`.
- `generatedBy = generatePegSolitaireLevel`.
- Difficulty estimated from peg count, legal move count, target strictness, and center occupancy.

**Rigorous claim 7: the current difficulty score is heuristic, not a theorem.** `getDifficulty` combines peg load, mobility pressure, goal strictness, and center penalty into a 0-100 score. It explains why a position may feel hard, but it does not prove exact human difficulty or exact shortest-search depth.

**Hook 6: the generator's baseline is a health certificate, not a Michelin star.** First it proves the puzzle is edible: the target is reachable. Later versions can chase finer taste: uniqueness, drama, symmetry breaks, and calibrated difficulty. v1 hangs the health certificate on the wall and refuses to pretend it has already won stars.

Future stronger guarantees can be layered in:

- Unique solution: enumerate or count all routes to target, at much higher cost.
- Unique shortest solution: search through the shortest depth layer and count target routes at that layer.
- Difficulty calibration: add features such as dead-end density, symmetry breaking, and center-return distance, then fit them to playtest data.

Open question for players and developers: is a good Peg Solitaire puzzle one whose shortest solution is hard to find, or one whose final few jumps feel dramatic?
